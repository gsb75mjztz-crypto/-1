## Entry #1 detail — duplicated disclosure logic

**Why it exists:** `MetricExplain.tsx` was built as new, self-contained code for the Comparison Tool rather than by refactoring `Badge.tsx` to share a primitive, specifically to avoid touching existing, already-shipped, heavily-audited code as part of an unrelated milestone.

**Why it's deferred, not fixed, now (engineering reasoning, not scope):**

- The duplication is small — roughly 15–20 lines of toggle mechanics. This codebase's own established threshold for "duplication justifies an extraction" is three independent occurrences, not two (`lib/cn.ts` was extracted only after the same className-merge logic was hand-rolled identically three times — see `handover/Milestone-2.md`).
- `Badge.tsx` renders the confidence-badge tooltip, including the "not a rating of the fund" clause the Legal Principles doc calls non-negotiable. It is the single most regulatory-sensitive, most heavily re-verified component in the product. Refactoring it to share a primitive with `MetricExplain` means re-earning that verification (exact tooltip copy, contrast, focus, screen-reader behaviour) for a ~15-line saving — a poor risk/benefit trade regardless of which milestone is in progress.
- Two data points aren't enough to know the right shared shape. `MetricExplain`'s panel takes arbitrary children; `Badge`'s panel has fixed internal structure (a bolded clause plus a link to Methodology). Guessing at an abstraction now risks building one that fits neither well, requiring a second reshape once a real third use case defines the actual requirements.

**Resolution condition:** revisit when a third disclosure-pattern use case appears — most likely a Calculator result explanation, per the Development Roadmap's Week 4 scope. Extract from three real implementations at that point, not from two plus a guess.

## Entry #2 detail — validation sprint not yet run

**What the doc requires:** `docs/InvestorHub-validation-sprint.md` specifies 20 user interviews, a survey, a landing-page smoke test, and X content validation, explicitly sequenced to run "before any product code gets written," with the stated purpose being to find out for real whether the answer is no — not to collect polite encouragement after the fact.

**What actually happened:** none of it, as of Milestone 5's kickoff. Confirmed directly: "There have been no interviews/survey/landing-page test, these are all in planning and to be conducted." Four milestones (Foundation, Homepage/Trust, ETF pages, Comparison Tool) plus one optimisation pass have shipped in that time.

**Why this is recorded here rather than silently proceeding:** this is the single largest risk on the project, and it's not a technical one — no amount of code quality, test coverage, or audit rigor substitutes for knowing whether active-beginner investors actually want this tool. Recording it explicitly is what keeps it from being quietly assumed-away by the momentum of continued feature work.

**The decision, on record:** presented as an explicit choice — pause Milestone 5 and validate first, run validation in parallel with continued building, or proceed to Milestone 5 and validate later. The product owner chose to **proceed to Milestone 5 and validate later**, a deliberate, informed deferral, not an oversight.

**Resolution condition:** not a code trigger. Revisit if real usage or feedback from Milestone 5 onward contradicts assumptions the build has been making (e.g. the curated-fund selection, the comparison-first user flow, the fee-drag framing) — at that point the cost of having skipped validation becomes concrete rather than theoretical, and it should force a stop, not just another engineering iteration.
